# Research: CI/CD agentic code review — GHA workflow around `packages/code-reviewer`

**Date**: 2026-09-11T08:17:13+02:00
**Researcher**: Sebastian Urbański
**Git Commit**: ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630
**Branch**: master
**Repository**: 10xCards

## Research Question

Based on [context/changes/ci-cd-code-review/requirements.md](requirements.md): how should a new GitHub Actions workflow that runs an AI code review (via `packages/code-reviewer`) on every pull request to `master` be built, given what already exists in this codebase — the reviewer package itself, the existing `ci.yml`, and any prior planning/conventions for GHA automation?

## Summary

Three things are true simultaneously and shape everything else:

1. **`packages/code-reviewer` cannot satisfy the requirements as it stands today.** It takes one opaque text blob in, produces `{summary, issues[severity, message]}` out, has no argv parsing, and its `ReviewSchema` has no per-criterion score field. All four gaps the requirements doc already calls out are confirmed live in the code, not hypothetical — this is a package change, not just a GHA wrapper, before any workflow can be written.
2. **The GHA/automation side is greenfield in the live repo** (no composite action, no label logic, no `gh`/octokit usage anywhere in `.github/workflows/ci.yml`) **but not greenfield in design** — a fully worked, structurally near-identical template already exists at [.claude/skills/10x-impl-review-ci/references/workflow-template.yml](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/.claude/skills/10x-impl-review-ci/references/workflow-template.yml), built for a sibling feature (`/10x-impl-review-ci`). It demonstrates every mechanic this feature needs: label-gated triggering including `labeled`/`unlabeled`, fork-PR exclusion, per-job `permissions`, PR-number-scoped `concurrency`, posting a manual commit status, reading PR labels via `gh pr view --json labels`, and a guard step to avoid re-running on bot/label-only events. It is a *pattern* source, not a drop-in — it invokes `anthropics/claude-code-action@v1` against `ANTHROPIC_API_KEY`, whereas this feature needs to build+run the `packages/code-reviewer` TS package (OpenRouter-backed) and script the PR comment/label itself.
3. **`ci.yml`'s own `e2e`/`db-tests` jobs, and the impl-review that hardened them, are the second pattern source** — they establish the house conventions for *this specific repo's* `ci.yml` file (as opposed to the imported skill template): workflow-level `permissions: contents: read` + `concurrency` group named `${{ github.workflow }}-${{ github.ref }}`, `persist-credentials: false` on non-writing checkouts, `if: github.event_name == 'pull_request' && github.event.pull_request.head.repo.full_name == github.repository` for fork exclusion, one job per concern, named steps that fail loudly, and never letting an artifact carry secrets/sensitive payloads.

No document in the repo anticipated this exact feature before today — `packages/code-reviewer`'s own origin (`context/archive/2026-09-10-tool-loop-agent/`) only imagined a future *promptfoo eval* consumer, never a GHA PR-review consumer. The schema/CLI gaps were preserved deliberately as an "empty seam," not because someone planned to fill them with CI.

## Detailed Findings

### `packages/code-reviewer` — what exists today, and the four things that must change

The package is a standalone Node ≥24 ESM project (own `package.json`, lockfile, `node_modules`), **not an npm workspace of the root** (root `package.json` has no `workspaces` field — confirmed absent), matching requirements.md's own note.

- **Schema has no per-criterion score.** [packages/code-reviewer/src/schemas/review.ts](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/packages/code-reviewer/src/schemas/review.ts) is `{ summary: string, issues: [{severity: 'low'|'medium'|'high', message: string}] }`. Requirements.md's six 1–10 scored criteria (correctness, idiomaticity, complexity, test/risk coverage, documentation, security) have no home in this shape yet — this is the gap the requirements doc itself flags (line 18), and it's confirmed as the actual current shape, not stale.
- **Agent is genuinely tool-less, single-step, and this was a deliberate, documented choice** — not an oversight to silently work around. [packages/code-reviewer/src/agent/tools.ts](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/packages/code-reviewer/src/agent/tools.ts) is literally `export const reviewerTools = {} satisfies ToolSet;` with a comment that the loop is intentionally single-step and that adding any tool requires an explicit `stopWhen` (the SDK default allows 20 paid steps). [packages/code-reviewer/src/agent/reviewer.ts:8-9](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/packages/code-reviewer/src/agent/reviewer.ts#L8-L9) hard-caps `maxOutputTokens` at 2048 specifically because OpenRouter reserves the model's full max output (65k tokens) against credits otherwise.
- **`cli.ts` has no argv parsing and no concept of separate inputs.** [packages/code-reviewer/src/cli.ts](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/packages/code-reviewer/src/cli.ts) joins all argv into one string (`process.argv.slice(2).join(' ')`) and passes it as a single `code` string to `reviewCode`. There is no flag/parsing library (no yargs/commander/`util.parseArgs`). Requirements.md's three distinct inputs (PR title, PR description, git diff) have nowhere to land as separate fields — they'd either get concatenated into one blob ahead of the existing single-string path, or `cli.ts`/`buildReviewPrompt`/`ReviewSchema` need a source change. The prompt wrapper's tag name itself, `<code_to_review>` ([packages/code-reviewer/src/prompts/reviewer.ts:14](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/packages/code-reviewer/src/prompts/reviewer.ts#L14)), implies code, not a PR-metadata bundle — a concatenation shortcut would be semantically off from what the model is told it's reading.
- **Prompt-injection handling in `buildReviewPrompt` is solid and reusable.** [packages/code-reviewer/src/prompts/reviewer.ts:6-8](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/packages/code-reviewer/src/prompts/reviewer.ts#L6-L8) neutralizes any `<`/fullwidth-`＜` sequence that could open/close the `<code_to_review>` tag inside untrusted input, tested against 8 case/spacing/unicode variants in [packages/code-reviewer/src/prompts/reviewer.test.ts:16-33](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/packages/code-reviewer/src/prompts/reviewer.test.ts#L16-L33). Whatever shape the new prompt-building takes for title+description+diff, this pattern (and its test style) is the one to extend rather than reinvent, since a PR title/description is exactly the kind of untrusted, model-readable text this guard was built for.
- **Build output is not checked in.** `dist/` is gitignored via the root `.gitignore`'s unscoped `dist/` entry — a GHA step must run `npm ci && npm run build` in `packages/code-reviewer` itself before anything under `dist/` exists, exactly as requirements.md states. `npm run build` = `tsc -p tsconfig.build.json` ([packages/code-reviewer/package.json:14](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/packages/code-reviewer/package.json#L14)), which extends `tsconfig.json` and only excludes `*.test.ts` — no other compiler-option differences. `main` is `dist/index.js`.
- **Tests are fully mocked — no `OPENROUTER_API_KEY` needed for `npm test`.** [packages/code-reviewer/src/agent/reviewer.test.ts](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/packages/code-reviewer/src/agent/reviewer.test.ts) uses `MockLanguageModelV4` from `ai/test`, entirely in-process. [packages/code-reviewer/src/index.test.ts:14-27](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/packages/code-reviewer/src/index.test.ts#L14-L27) deliberately stubs an *empty* API key so config validation fails fast, before any network call would be attempted — the test suite is specifically designed never to reach the network. This means a CI `test` step needs no secret; only the actual review-invocation step does.
- **Node version**: package requires `>=24` ([packages/code-reviewer/package.json:8](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/packages/code-reviewer/package.json#L8)); repo's `.nvmrc` pins `24.19.0`; `ci.yml` uses the bare major `24` in `actions/setup-node@v4` — compatible, not byte-identical. A new job should match `ci.yml`'s existing `node-version: 24` convention rather than introduce a third pin style.
- **Fully isolated from root tooling.** Root `eslint.config.js`, `.prettierignore`, root `tsconfig.json`, and `vitest.config.ts` all explicitly exclude `packages/**` with matching Polish-language comments ("Packages are standalone projects with their own toolchain — root doesn't lint/format/typecheck them"). `packages/code-reviewer` has no ESLint or Prettier config of its own — any CI step touching it (lint, format-check) must either skip that check or be added net-new inside the package, since none exists today.
- **No env/version drift found**: `.env.example` matches `config.ts`'s zod default (`anthropic/claude-sonnet-5`) exactly; `zod@4.6.1` inside the package vs. root's `zod@4.4.3` is not a real conflict since the package has its own `node_modules` tree.

### GitHub Actions — existing conventions in this repo's `ci.yml`

[.github/workflows/ci.yml](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/.github/workflows/ci.yml) has three jobs (`ci`, `db-tests`, `e2e`) and is the only live workflow (`.github/workflows/` contains nothing else; no `.github/actions/`, no `action.yml` anywhere in the repo — a new composite action is genuinely being created from scratch, confirming requirements.md).

Conventions, each traceable to an explicit review finding, not just style:

- **Workflow-level `permissions: contents: read`** ([ci.yml:13-14](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/.github/workflows/ci.yml#L13-L14)), added via [context/archive/2026-09-07-testing-e2e-critical-loop/reviews/impl-review.md](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/context/archive/2026-09-07-testing-e2e-critical-loop/reviews/impl-review.md) finding F6, together with `persist-credentials: false` on checkouts that don't write ([ci.yml:54-56](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/.github/workflows/ci.yml#L54-L56), [ci.yml:100-102](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/.github/workflows/ci.yml#L100-L102)). A job that needs to write (post a comment, add a label) must override this with its own job-level `permissions:` block — `ci.yml` has no precedent for that yet, but the skill template does ([.claude/skills/10x-impl-review-ci/references/workflow-template.yml:52-57](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/.claude/skills/10x-impl-review-ci/references/workflow-template.yml#L52-L57)): `contents: write`, `pull-requests: write`, `statuses: write`, scoped per-job under a top-level `permissions: {}`.
- **Fork-PR exclusion**, `e2e` job condition ([ci.yml:91](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/.github/workflows/ci.yml#L91)): `if: github.event_name == 'pull_request' && github.event.pull_request.head.repo.full_name == github.repository`, with the reasoning spelled out in the adjacent comment ([ci.yml:86-90](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/.github/workflows/ci.yml#L86-L90)) — trigger is `pull_request` (never `pull_request_target`), so forks get no secrets, and it's better to skip the job than fail it for a reason unrelated to the change. Requirements.md (line 6) explicitly points back at this exact pattern for the new review job.
- **Workflow-level `concurrency`**, `${{ github.workflow }}-${{ github.ref }}` with `cancel-in-progress: true` ([ci.yml:19-21](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/.github/workflows/ci.yml#L19-L21)) — added via the same impl-review pass, finding F10, to stop overlapping Supabase stacks on rapid pushes. The skill template instead scopes `concurrency` per-job to the PR number ([workflow-template.yml:48-50](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/.claude/skills/10x-impl-review-ci/references/workflow-template.yml#L48-L50)) — either convention is attested in this repo; the ref-scoped one is what's actually live in `ci.yml` today.
- **`timeout-minutes`** on any job that can hang (`e2e`: 20 minutes, [ci.yml:96](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/.github/workflows/ci.yml#L96)) — same F10 finding. A code-review job calling an LLM should carry an analogous cap.
- **One job per concern, named steps that fail loudly under their own name** — explicit rationale in [context/archive/2026-09-07-testing-e2e-critical-loop/plan.md:406-407](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/context/archive/2026-09-07-testing-e2e-critical-loop/plan.md): folding `e2e` into `db-tests` would let a pgTAP failure mask the e2e result, so they're kept separate. The same logic argues for the review job being its own job, not steps bolted onto `ci`.
- **Artifacts and logs never carry secrets or sensitive payloads** — [ci.yml:168-175](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/.github/workflows/ci.yml#L168-L175)'s comment on why only `playwright-report/` (never `test-results/`, which holds a trace with a typed password) is uploaded: GitHub's `::add-mask::` masks logs, never artifact contents. Directly relevant here since a code-review job's failure debugging would naturally want to dump the LLM's raw response — that must not include the diff/prompt if the diff could contain secrets, or must be handled the same deliberate way.
- **Deploy is deliberately excluded from `ci.yml`** — established in [context/archive/2026-08-17-deployment/deployment-plan.md:91](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/context/archive/2026-08-17-deployment/deployment-plan.md), reinforced in `context/foundation/roadmap.md:71`. Not directly relevant to the review job, but confirms the "each workflow/job owns exactly one concern" norm holds repo-wide, not just within `ci.yml`.

### The `10x-impl-review-ci` skill template — a near-complete pattern library for this feature

[.claude/skills/10x-impl-review-ci/references/workflow-template.yml](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/.claude/skills/10x-impl-review-ci/references/workflow-template.yml) is a full, commented GHA workflow built for a sibling AI-PR-automation feature. It is not wired into this repo's live CI (no `.github/workflows/impl-review.yml` exists) and it calls a different mechanism (`anthropics/claude-code-action@v1` against `ANTHROPIC_API_KEY`, not the `packages/code-reviewer`/OpenRouter path this feature needs) — so it cannot be copied wholesale, but every GHA *mechanic* requirements.md asks for has a worked example here:

- **On-demand retry via label**, exactly what requirements.md (lines 56-58) asks for: `on.pull_request.types: [opened, synchronize, reopened, labeled, unlabeled]` ([workflow-template.yml:28-34](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/.claude/skills/10x-impl-review-ci/references/workflow-template.yml#L28-L34)), gated with `contains(github.event.pull_request.labels.*.name, 'impl-review')` ([:47](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/.claude/skills/10x-impl-review-ci/references/workflow-template.yml#L47)) — the direct template for gating on `ai-cr:review` being added, including the comment explaining *why* `labeled`/`unlabeled` must be in the trigger list (plain `pull_request` won't fire on a label add — the same fact requirements.md line 57 states independently).
- **Reading PR labels via `gh` CLI**: `gh pr view "$PR_NUMBER" --json labels --jq '...'` ([:289-290](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/.claude/skills/10x-impl-review-ci/references/workflow-template.yml#L289-L290)) — usable as-is for checking/toggling `ai-cr:passed`/`ai-cr:failed`.
- **Posting a manual commit status** (parallel concept to a PR comment/label) via `gh api --method POST "repos/{owner}/{repo}/statuses/${HEAD_SHA}"` ([:241-247](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/.claude/skills/10x-impl-review-ci/references/workflow-template.yml#L241-L247)) — and the reasoning for why it's manual rather than relying on GHA's implicit check ([:228-233](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/.claude/skills/10x-impl-review-ci/references/workflow-template.yml#L228-L233)).
- **A guard step to avoid infinite/wasted re-runs** — checks the last commit's author/subject and the event action before deciding whether to actually invoke the model ([:80-102](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/.claude/skills/10x-impl-review-ci/references/workflow-template.yml#L80-L102)). This feature's analogue: avoid re-reviewing on every push if nothing changed, or re-running the full review on a bare label toggle when only the pass/fail label state needs re-evaluating.
- **Verdict parsing → gate → override label** ([:262-300](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/.claude/skills/10x-impl-review-ci/references/workflow-template.yml#L262-L300)): parses a verdict out of a committed markdown report, fails the job unless a specific override label (`impl-review-override`) is present — directly analogous to requirements.md's open question about a pass/fail rule, and a concrete precedent for "a label can bypass a red gate" if that's the desired escape hatch here too.
- **Per-job `permissions` scoped tightly** (`contents: write`, `pull-requests: write`, `statuses: write` — [:52-57](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/.claude/skills/10x-impl-review-ci/references/workflow-template.yml#L52-L57)), the template this repo's `ci.yml` doesn't yet need but this feature will.

### Historical context — `packages/code-reviewer`'s origin and what was consciously deferred

No `plan.md`/`research.md` documents the package's *original* creation — it predates the `context/`-driven workflow entirely and was "untracked in git" before [context/archive/2026-09-10-tool-loop-agent/](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/context/archive/2026-09-10-tool-loop-agent/), which only **refactored** an existing one-file script into the current module layout. That refactor's plan is explicit that it changed no contracts: *"No schema contract changes: field names, types and enum values stay the same. Only `.describe()` text is added"* ([context/archive/2026-09-10-tool-loop-agent/plan.md:79](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/context/archive/2026-09-10-tool-loop-agent/plan.md#L79)) and *"No agent tools. `src/agent/tools.ts` is an empty seam"* ([plan.md:78](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/context/archive/2026-09-10-tool-loop-agent/plan.md#L78)).

The only anticipated future consumer named anywhere is a **promptfoo eval provider** ([context/archive/2026-09-10-tool-loop-agent/plan-brief.md:6-11](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/context/archive/2026-09-10-tool-loop-agent/plan-brief.md#L6-L11)) — no promptfoo change folder exists yet. This CI/CD feature is genuinely new scope, not a roadmap item being picked up; `context/foundation/roadmap.md`, `prd.md`, and `tech-stack.md` contain zero mentions of "code review" as a product concern (only generic "CI does lint + build" notes).

Deferred items already queued for `packages/code-reviewer`, recorded in [context/archive/2026-09-10-tool-loop-agent/follow-ups/review-fixes.md](https://github.com/sebast82/10xCards/blob/ecb5b7796c7d50afb7d1e0d0ddb6a1950372c630/context/archive/2026-09-10-tool-loop-agent/follow-ups/review-fixes.md), several of which a CI caller should care about directly:
- No `abortSignal`/timeout is threaded into `agent.generate()` yet — a hung OpenRouter call has no CI-side timeout from the package itself (the calling job's own `timeout-minutes` would be the only backstop).
- No input-size cap — large diffs go to the model uncapped.
- `maxRetries` is the SDK default (2, i.e. up to 3 paid attempts per failing review) — relevant to CI cost/latency on a busy PR.
- A noted risk that `APICallError.requestBodyValues` carries the full reviewed input — "a provider should log `error.message` only," directly relevant to the "don't leak sensitive payloads into CI logs/artifacts" convention already established in `ci.yml`.

## Architecture Insights

- **Two separate "prior art" sources, two separate purposes.** `ci.yml` + its impl-review history tells you the conventions *this repo's own* GHA files must follow (permissions, concurrency, fork handling, one-job-per-concern). The `10x-impl-review-ci` skill template tells you the *mechanics* of PR-automation-via-label-and-comment that don't exist in `ci.yml` yet (label gating, `gh pr view --json labels`, commit-status posting, override-label bypass). Neither alone is sufficient; the new workflow is a merge of both idioms into a third, `packages/code-reviewer`/OpenRouter-flavored implementation — it should not adopt `claude-code-action@v1`, since the whole point of `packages/code-reviewer` is a standalone, OpenRouter-backed reviewer, not the Claude Code agent CLI.
- **The v1 tool-less agent was a *seam*, not a temporary hack awaiting removal.** The requirements doc frames it as a known limitation to state, not fix — that matches the package's own history exactly (an "empty seam" by design, contracted around explicit `stopWhen` risk if a tool is later added). This lowers the urgency of adding repo-read tools for this change; treat it as out of scope unless a later change explicitly revisits it.
- **The schema/CLI gap is the actual blocking dependency, not the GHA wrapper.** Every piece of the GHA design (composite action, labels, retry) is buildable against the *current* package shape by concatenating title+description+diff into one blob — but that would misrepresent per-criterion scoring, which the requirements explicitly want surfaced (six 1–10 scores, pass/fail rule TBD). The package change (schema + prompt + some entry point that accepts three named inputs) should be sequenced before or alongside the workflow, not after.
- **Cost tradeoff flagged in requirements.md ("PR description (?? cost tradeoff)")** has no existing answer in the codebase — nothing in `packages/code-reviewer` or its history discusses input-size/cost tradeoffs beyond the generic deferred "input-size cap" note above. This is a genuinely open design question, not something research surfaced an answer to.
